# Data protocol: what is pushed, what is not, and how raw/ is rebuilt

## 1. What goes where

| Content | Where | In git? | Why |
|---|---|---|---|
| Code (`tools/`, `setup.*`) | repo | yes | |
| Catalog metadata (`catalog/metadata/`, `catalog/manifests/`) | repo | yes | small (~7 MB), diffable between iterations |
| Provenance (`catalog/sources/registry.json`, `<lib>.json`, `<lib>.sha256`, `mirror.json`) | repo | yes | the reference every download is checked against |
| Potential files (`raw/<lib>/…`, ~9 GB) | maintainer's disk + GitHub Release assets | **no** | too large for git; upstream licences apply |
| Rebuilt output (`catalog/views/`, `catalog/metadata/parsed_headers/`) | local only | no | regenerated by `run_pipeline.py` |
| Mirror archives (`dist/mirror/`) | local, then uploaded | no | uploaded as Release assets |

Never `git add -f` anything under `raw/` or `dist/`.

## 2. How a user gets all files (one command)

`./setup.sh` / `.\setup.ps1` runs `tools/fetch_all.py`, which for each library:

1. skips it if `raw/<lib>` already matches `catalog/sources/<lib>.sha256`;
2. otherwise downloads it from the **mirror**: the GitHub Release listed in
   `catalog/sources/mirror.json` (an exact copy of the maintainer's `raw/`,
   split into ≤1.9 GB parts, each SHA-256-checked);
3. if there is no mirror or it fails, runs the **upstream recipe** from
   `registry.json` (git clone at a pinned commit, direct files with checksums,
   or a scraper in `tools/fetch/`);
4. verifies again; files that differ from the manifest are reported, and the
   exit code is non-zero if any library is incomplete.

Generated bookkeeping files (download summaries, inventories, `.extracted`
markers) may differ without making a library incomplete.

### Upstream reproducibility (tested 2026-11-10)

| Library | From upstream alone | Notes |
|---|---|---|
| BLPSLibrary, pseudos_ac_she | exact | pinned git commits, cloned with `core.autocrlf=false` |
| SG15-ONCV | exact | 2020 tarball, 2015 tarball over it, 64 `_FR` files fetched individually |
| SSSP v1.0–1.3 | exact | Materials Cloud record `rcyfm-68h65`, md5 from its API |
| SSSP v2.0, v0.7, `SSSP_1.0_plots.tar.gz` | **no** | no public download found; **mirror only** |
| PSlibrary, Vanderbilt-USPP | scraper | site reachable; output not yet compared byte-for-byte |
| PseudoDOJO | scraper | TLS verification failed from the maintainer's machine; install `certifi` |
| PWmat, Rappe-group | scraper | sites answered 403 to scripted requests; **mirror needed** |

So the mirror is what makes setup one-command. Until it is published,
`fetch_all` completes BLPS, pseudos_ac_she, SG15 and SSSP v1.x and reports the rest.

## 3. Maintainer: publishing the mirror

Do this once per data release (e.g. tag `raw-2026.11`).

1. **Licences.** For every library you are about to publish, confirm in
   `registry.json` that the upstream licence allows redistribution and set
   `license_verified: true`. Libraries with `license: null` (PWmat, Rappe,
   GBRV, pseudos_ac_she) must be checked first; leave unclear ones out of the
   mirror (they then fall back to their scraper).
2. **Verify raw/** is what you mean to publish:
   `python tools/record_sources.py --verify` → all `ok`.
3. **Pack** (needs free disk ≈ size of the libraries packed):
   `python tools/pack_mirror.py --tag raw-2026.11 SSSP PSlibrary PseudoDOJO ...`
   This writes `dist/mirror/*.tar.gz[.partNNN]` and `catalog/sources/mirror.json`.
4. **Upload** (fine-grained token with *Contents: read and write* on the repo):
   PowerShell `$env:GITHUB_TOKEN = "<token>"; python tools/publish_mirror.py`
   (re-run safely after an interruption; finished assets are skipped).
5. **Test from scratch** on a clean directory:
   `POTDEX_RAW=/tmp/potdex-test python tools/fetch_all.py --mirror-only`
6. **Commit and push** `catalog/sources/mirror.json`. Only now do users see the mirror.

## 4. Maintainer: changing raw/

Any deliberate change to raw/ (new library, new version, repaired file):

1. add or update the library in `catalog/sources/registry.json` (URL, licence, upstream steps);
2. put the files in `raw/<lib>/` (preferably with `python tools/fetch_all.py <lib> --upstream`);
3. `python tools/record_sources.py <lib>`: new manifest; review `git diff catalog/sources/`;
4. `python tools/run_pipeline.py`: rebuild the catalog; check `catalog/metadata/validation_report.json`;
5. if the library is in the mirror, repack and publish under a **new** tag (never replace assets of a published tag);
6. commit registry, manifests, catalog metadata and `mirror.json` together.

Rule: the pipeline reads raw/ but never writes to it. `record_sources.py --verify`
must stay clean after `run_pipeline.py`.

## 5. Push checklist (code changes)

- [ ] `python tools/run_pipeline.py` passes; `validation_report.json` has `"ok": true`
- [ ] `python tools/record_sources.py --verify` all `ok`
- [ ] `git status` shows nothing under `raw/`, `dist/`, `catalog/views/`
- [ ] counts in `catalog/metadata/coverage_report.json` changed only where intended
- [ ] commit message says which libraries or families changed
